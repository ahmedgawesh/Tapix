Open questions / risks parked for later phases
───────────────────────────────────────────────────────────────

Q1 (Phase 2 engine-readiness audit):
    SaleLineItem.totalCents today hard-codes
        taxCentsWithSettings(enableTaxCalculations: true, defaultTaxRateBps: 0)
    meaning the line's OWN `totalCents` ignores the invoice's
    `enableTaxCalculations`/`defaultSalesTaxRateBps` settings. The invoice
    aggregate (`SaleFormState.itemTaxCents`) DOES respect them. Goldens
    must pin both behaviours as-is.

Q1b (discovered 2026-05-12 while writing sale goldens):
    TaxCalculationService.resolveLineItemTaxRateBps falls through to
    `defaultTaxRateBps` EVEN WHEN `product.isTaxable == false`. A
    non-taxable product sold in an invoice with a configured default
    sales-tax rate is charged at the default rate. This is the documented
    contract (tax_calculation_service.dart:285-296) but may surprise
    users who expect `isTaxable=false` to be a veto. Pin as-is (see
    sale_form_pricing_golden_test.dart S11); if changed, it is an ADR-
    worthy product decision, not a migration artefact.

Q2 (Phase 2):
    SaleFormState.loyaltyDiscountCents is subtracted AFTER tax
    (post-tax discount). InvoicePricingEngine does not currently model a
    post-tax adjustment. Decision for Phase 4: keep loyalty reduction in
    the bloc's `_TenderSnapshot`, NOT in the engine.

Q3 (Phase 2):
    PurchaseFormState.effectiveInvoiceDiscountCents uses
        (subtotalCents * invoiceDiscountPercent / 100).round()  → Decimal
    with clamp-to-subtotal. InvoicePricingEngine's overall-discount
    base is `Σ line.net` (net-of-item-discounts), not subtotal. For a
    purchase with per-item discounts + invoice-level percent, these
    differ. Phase 3 MUST resolve this by routing invoice-level percent
    through `Discount.percent(bps)` and consuming engine output.

Q4 (Phase 1):
    journal_repository_impl.dart:256-280 is a SECOND writer of
    accounts.balance_cents alongside accounting_repository.dart:744-777.
    Race/divergence risk. Fix BEFORE any bloc migration.

Q5 (discovered 2026-05-12 while writing property tests):
    InvoicePricingEngine's "1% per-item ≡ 1% overall" invariant is
    EXACT only on friendly equal-weight inputs. On arbitrary weights,
    the per-line-rounded path and the overall-proration path may drift
    by up to 1 cent per line. This is mathematically expected (two
    independent rounding chains) and is NOT a bug. The bug the engine
    CLOSES is "base includes tax" (ΔΔ cents from 799.84 to 799.92),
    not "byte-identical results". Documented inside the property test.

    → Implication for Phase 3/4 migration: dual-compute assertions
      comparing the legacy bloc math with the engine math MUST tolerate
      a ≤ 1-cent-per-line drift when the bloc happens to round differently.
      We'll pin the EXACT bloc outputs via the Phase-0 goldens and only
      intentionally diverge when an ADR approves.

    → Next: run `flutter test test/golden test/core/pricing` and commit
      as the phase-0 safety net. Optional: trial-balance parity test
      between accounting_repository and journal_repository_impl.

[2.2] Q-log resolutions:
    Q2 — Loyalty redemption is TENDER, not pricing.
         Rationale: GAAP/IFRS-15 revenue is the gross transaction price;
         loyalty redemption is a contra-AR settlement (not a price
         reduction). Pricing engine emits pre-loyalty total; the bloc
         applies the loyalty deduction in a _TenderSnapshot equivalent.
         CLOSED.

    Q3 — Purchase invoice-discount base mismatch (subtotal vs Σ net):
         The engine's base (Σ net) and the bloc's base (subtotal) differ
         only when per-line discounts AND an invoice discount coexist.
         tapix's `discountMode` is `perItem | invoice` (exclusive), so
         when `discountMode == invoice` per-line discounts are bypassed
         (TaxCalculationService.calculateInvoiceTax overwrites them) and
         Σ net == subtotal. The engine model is a strict superset;
         current usage hits the intersection. CLOSED.
         → Invariant test required in Phase 3 to pin mode exclusivity.

[2.3] Engine capability gaps — NONE require engine code changes.
    Only thin bloc-side adapters needed:
      G1: Decimal→Money at the boundary via
          `Money.fromCents(d.toBigInt().toInt())`.
      G2: Decimal percent → bps inline:  `(percent × 100).round()`.
      G6: `toPricingInput()` extension on each line type, mirroring
          AdjReturnLineItem.toPricingInput() (the already-migrated
          reference implementation).
      G7: Discount-mode bridging at the bloc layer (perItem ⇒ per-line
          Discount, invoice ⇒ overallDiscount + per-line Discount.none).
    G3/G4/G5 are documented as design intent, not gaps.

    Both already consume InvoicePricingEngine via a memoized

[5.1] ReturnCalculationService extended (sole writer of rollup totals).
    + typedef ReturnLineAmounts = ({int subtotalCents, int discountCents,
        int taxCents, int refundCents, int quantity});
      A Dart record describing one line's contribution to a rollup.
    + class ReturnRollup — value type carrying the five aggregated ints
      plus a static ReturnRollup.empty constant.
    + static ReturnCalculationService.aggregate(Iterable<ReturnLineAmounts>)
      — single integer-additive accumulator. No rounding, no division;
      Σ(parts) is exactly the result.

[5.2] SaleReturnFormState migrated.
    + Dropped `const` from the constructor so it can host a `late final`
      memoized rollup (mirrors PurchaseFormState / SaleFormState shape).
    + late final ReturnRollup _rollup =
        ReturnCalculationService.aggregate(returnItems.map(...));
      Built once per immutable state instance, reused by every total
      getter so they can never disagree.
    + The four `fold(Decimal.zero, +)` loops + the `fold(0, +)` quantity
      loop REPLACED — each total getter now reads from _rollup:
          totalSubtotalCents   ← Decimal.fromInt(_rollup.subtotalCents)
          totalDiscountCents   ← Decimal.fromInt(_rollup.discountCents)
          totalTaxCents        ← Decimal.fromInt(_rollup.taxCents)
          totalRefundCents     ← Decimal.fromInt(_rollup.refundCents)

Phase 8 — Lints & Tooling Enforcement (Regression Prevention)
───────────────────────────────────────────────────────────────

Goal: Lock in every Phase 1–7 invariant via a mechanized guard that
fails CI the moment anyone re-introduces a banned pattern. Dart has
no built-in lint for the patterns we want to ban, and a custom
`analyzer` plugin would be heavyweight for the surface we need.
Instead: a single static-analysis test that scans `lib/**/*.dart`
(with comments stripped so prose can't trip regexes) and asserts
each banned pattern is absent — or present only in an explicit
allow-list with a documented reason.

The guards are TIERED:
  * Tier 1 (zero tolerance): patterns Phases 1–7 closed in full.
    Any new occurrence anywhere fails CI.
  * Tier 2 (allow-listed ratchet): patterns where the SoT exists
    but a small set of UI sites have not yet migrated. The
    allow-list pins the current set; any NEW offender outside the
    list fails. The list can only shrink — never grow.

[11.3a] Single-currency invariant in createJournalEntry.

  Problem.
    Every journal_entry_lines row carries its own currencyId, and
    no validator ensured all lines of one entry agreed. A
    mathematically balanced (Σdebits = Σcredits) but
    cross-currency entry would post silently — but with no
    realised/unrealised FX gain-loss account modelled in the seed
    CoA, the resulting GL would be economically meaningless.

  Fix.
    + In `AccountingRepository.createJournalEntry`, after the
      double-entry + minimum-lines checks, validate:
        entryData.lines.map((l) => l.currencyId).toSet().length == 1
      otherwise throw AccountingException('Journal entry mixes
      currencies ...'). Fires BEFORE the transaction opens, so no
      DB mutation occurs.
    + `journal_repository_impl.createJournalEntryWithLines`
      already delegates here (Phase-9) so the guard flows
      through every call site automatically — no second writer
      to patch.

PHASE 14.2 — DISCOUNT-MODE TOGGLE SYMMETRY                  2026-05-18
────────────────────────────────────────────────────────────────────

TRIGGER
-------
Field bug report on the purchase invoice form:
  1. User selects DiscountMode.perItem and enters per-line discounts.
  2. User changes their mind and toggles to DiscountMode.invoice.
  3. The previously-entered per-line discounts remain visible on

  4. The user worries this could cause a "double discount they

ROOT-CAUSE ANALYSIS (single root, two affected SoTs)
----------------------------------------------------
PurchaseFormBloc._onDiscountModeChanged and
SaleFormBloc._onDiscountModeChanged were ASYMMETRIC handlers:
both cleared `invoiceDiscountCents` (and `invoiceDiscountPercent`
for the purchase side) on mode switch, but neither cleared per-line
`discountCents` on `state.items` when switching INTO `invoice` mode.

The pricing engine (InvoicePricingEngine.compute) already masks
per-line discounts in invoice mode via the `overrideDiscount:
inInvoiceMode ? Discount.none : null` argument in `_computePricing`,
so the BOOKS were always correct (Q3 mode-exclusivity at
compute-time). But the STATE was leaky:

  * `state.itemDiscountCents` getter still summed the stale field
    and surfaced it in the UI.
  * The line-edit dialog reopened the line and prefilled the stale
    discount as if it were active.
  * Toggling back to `perItem` mode silently re-activated the old
    per-line discounts — the exact "double-discount the user can't
    notice" the user reported.

The proven reference pattern already existed in
`SaleAdjReturnFormBloc._onDiscountModeChanged` (Phase 11) with an
explicit code comment warning about EXACTLY this bug class:
  "Without this, item-level discounts would silently stack with
   a freshly-entered overall discount (or vice-versa), causing a
   'double-discount' bug where the same nominal 1% produces two
   different totals depending on which entry path was used."

The fix is to mirror that pattern in the two main forms.

FIXES (additive, single SoT, zero scattered code)
--------------------------------------------------
A. `lib/features/purchases/presentation/bloc/purchase_form_bloc.dart`
   `_onDiscountModeChanged` now:
     * On switch to `invoice` mode: maps every `state.items[i]`
       through `copyWith(discountCents: Decimal.zero)`.
     * On switch to `perItem` mode: keeps items as-is (they were
       already required to be clean while in invoice mode).
     * Continues to zero `invoiceDiscountCents` and
       `invoiceDiscountPercent` on every mode switch (existing
       behaviour, kept for symmetry).
     * Sets `hasUnsavedChanges: true` so the unsaved-changes guard
       fires correctly.

B. `lib/features/sales/presentation/bloc/sale_form_bloc.dart`
   `_onDiscountModeChanged` mirrors (A) symmetrically (no
   `invoiceDiscountPercent` field on the sale state).

C. Doc-comment refresh on `PurchaseFormState.itemDiscountCents` and
   `SaleFormState.itemDiscountCents` getters: the previous comment
   ("the UI still surfaces them so users can see what they
   previously entered before switching modes") was a description

DELIBERATELY UNCHANGED

ROOT CAUSE (single, upstream, in an existing SoT)

  The Phase-15.0 read formula in
  `lib/features/accounting/data/datasources/journal_local_datasource.dart`
  (`getTotalInventoryValueCents`) preferred `Σ(batch.remaining × unit_cost)`
  whenever ANY active batch existed for a variant. That predicate was the
  ROOT cause of an asymmetry with the write side:

    Write side (PurchaseDao.postPurchase):
      `BatchService.createBatchFromPurchase(...)` runs UNCONDITIONALLY for
      every tracked purchase line — Phase 6.4 unified the ledger so even
      WAC products get a `product_batches` row per purchase.

    Write side (PurchaseDao.postPurchaseReturn / SaleDao.postSaleReturn /
                AdjustmentReturnDao):
      `BatchService.consumeFifo(...)` is GATED by `_isFifoProduct(productId)`.
      WAC products' batches are NEVER decremented. The return path only
      adjusts `variant.stock_quantity` and posts the `1200 Inventory` GL
      leg.

    Read side (Phase 15.0):
      Treated active batches as authoritative for ALL costing methods.

  Result: every linked or adjustment purchase return against a WAC product
  silently produced a phantom drift of EXACTLY (returned_qty × unit_cost).
  In the field-report DB:
    * Purchase #2 line 5 — product 2 (WAC/standard), qty 10 × 9 900¢

      → GL 1200 Inventory   297 000 → 267 300    ✓
      → batch B5 remaining_quantity = 10  ✗  (should be 9, but WAC return
                                              path doesn't touch it)
    * Read formula: B5 × 9 900 = 99 000 instead of variant SoT 9 × 9 900
      = 89 100 → drift 9 900¢ exactly matching the screen.

FIX (additive, single SoT, no schema change, single file edited)

  A — `journal_local_datasource.dart` :: `getTotalInventoryValueCents`
      Mirror the `_isFifoProduct` predicate inside the SQL:

        Branch 1 (batch ledger) — `WHERE b.is_active = 1
            AND (p.inventory_tracking_type IN ('batch','batch_expiry')
                 OR p.costing_method = 'fifo')`
        Branch 2 (variant)      — `WHERE NOT (FIFO predicate)
                                   OR NOT EXISTS active batch for v.id`
        Branch 3 (product)      — same predicate as Branch 2 for products
                                   without variants

      The OR fallback inside Branches 2/3 keeps pre-Phase-6.4 legacy FIFO
      data visible (FIFO product without batches → variant fallback).

  No write-side change. There is intentionally no "consume batch on WAC
  return" code path — WAC has no FIFO ordering, the batch row has no SoT
  semantics for WAC products, and adding a write would only be a workaround
  for a read-side bug. The single rule going forward is: batch ledger is
  SoT iff product is FIFO. Read predicate matches write predicate.
