TapBix online development service

Scope
This is the first executable S7-A delivery: the existing event envelope, canonical
hash and supported contract names are shared with the Flutter local ledger.
PostgreSQL persists immutable events and independent delivery leases, under forced
company RLS. It never posts a second financial journal on receipt.
The Flutter HTTPS gateway implements the existing synchronization gateway contract.
A build-gated pilot settings screen now invokes it. The released app does not
expose this pilot. Keep online purchases disabled.

Local computer setup
1. Install PostgreSQL 16 tools, or extract the official Ubuntu 24.04 packages
   postgresql-16, postgresql-client-16 and libpq5 under:
   .buildlog/station7/runtime/pg
2. From repository root:
   python3 server/online/tool/local_postgres.py
   cd server/online
   dart pub get --enforce-lockfile
3. From repository root, start the API:
   python3 server/online/tool/run_local.py
4. Check http://127.0.0.1:45830/healthz
PostgreSQL binds 127.0.0.1:55432. It uses independent development/test databases,
SCRAM passwords in mode-0600 ignored files, and an application role that cannot
own schema tables, bypass RLS, or update/delete event history. No mobile or Linux
branch databases are opened or replaced. This is a development process, not an
installed auto-start service; restart it after a machine reboot.

Development company
   python3 server/online/tool/run_local.py run bin/provision_development.dart NEW_PRIVATE_JSON_PATH
The output contains a newly generated demo organization, branch, database and owner
token. The command accepts only loopback tapbix_online_dev and issues a seven-day
development grant. This is NOT RevenueCat verification or a production entitlement.
Keep the output below .buildlog; never commit it. Never share access tokens in logs.
The request-based pilot flow below binds to an existing local writer explicitly;
it does not implement historical bootstrap or commercial company enrollment.

HTTP protocol
Every /v1 request requires X-Organization-Id. Protected requests also require
Authorization: Bearer <token>. JSON POST bodies are limited to 2 MiB and batches to
50 events. The service serializes per-company commit/fan-out boundaries and retains
per-source sequence order; duplicate hashes are acknowledged without reapplying.
- POST /v1/session: authenticated organization/database/branch/name/role and stable relay ID.
  No access token is returned by this inspection endpoint.
- POST /v1/invitations (owner): databaseId, branchId, name. Ten-minute invite.
- POST /v1/enroll: databaseId, invitationCode. Uses the invite's fixed identity/name.
  A lost response can be retried for the same identity before invite expiry.
- POST /v1/sync/push: events using the shared v1 SyncEventEnvelope contract.
- POST /v1/sync/pull: optional limit (1..50); returns leaseToken and events.
- POST /v1/sync/ack: leaseToken and eventIds, only AFTER durable local application.
- GET /v1/events (owner): raw event envelopes, optional sourceDatabaseId and offset.
  This endpoint is a development inspection feed, not a completed financial report.
Only the owner writer can publish catalogue/location snapshots. Each branch has one
active database writer. A role token authenticates a branch service, not a cashier.
An API acceptance confirms durable relay storage, NOT stock receipt by the destination.
Actual receipt remains a separately authored event from the receiving branch.

Validation
   python3 server/online/tool/run_local.py test --reporter expanded
   python3 server/online/tool/verify_restore.py
   python3 server/online/tool/run_local.py flutter-test --reporter expanded
The integration suite requires tapbix_online_test and fails rather than silently
skipping when configuration is missing. The restore checker creates a uniquely named
throwaway database, compares fingerprints/deliveries/forced RLS, then drops only that
database. Backup files contain data and credentials and remain private/ignored.
CI uses a fresh PostgreSQL service and the same migration and tests, including
Flutter/SQLite -> HTTP -> PostgreSQL -> inbound projection. The bridge fixture
requires tapbix_online_test and exchanges its temporary credentials over a private
process pipe. It tests durable envelopes, 64-bit amounts, Unicode, and reopening
the SQLite file. It does not certify end-user accounting workflows over the internet.

Existing-writer client integration
OnlineBranchSyncService validates the authenticated server binding against the
local immutable organization/database/branch before storing a connection. Existing
LAN writer enrollment is required and is preserved. A timed invitation is exchanged
once; the saved credential, endpoint and binding live together in secure storage,
keyed by the local database identity. Configuration requires an authorization
callback; the pilot UI uses the existing active owner session and Pro policy,
and rejects dependent cashier/warehouse clients.
The service reuses OfflineSyncEventStore and the supplied business projector. Its
cloud delivery peer has relay_remote_events=false: only locally authored events
are uploaded, with a cursor independent of every LAN peer. Remote acknowledgement
follows durable local application. Concurrent refreshes coalesce; interrupted pushes
remain retryable and duplicate inbound events do not repeat their effects.
The pilot controller schedules exchanges while the app is active, and checks
immediately on resume. Successful idle polls wait 15 seconds; full batches drain
after one second. Transient failures back off from 5 to 160 seconds. Identity,
credential and entitlement failures stop automatic retries and remain visible.
Pause persists in the secure connection record; resume needs no new invitation.
This is not an OS background service. Existing history/bootstrap and physical
platform secure-storage validation remain gates.


Pilot setup on the development computer
Use only an isolated test company with existing LAN writer enrollment. The pilot
preserves its immutable local identities and existing LAN peers; it does not
replace databases or create a second set of business permissions.
1. Build the Flutter app with --dart-define=TAPBIX_ONLINE_PILOT=true.
   For the same-computer development API only, also use
   --dart-define=TAPBIX_ONLINE_LOOPBACK=true. Network devices require HTTPS.
2. Sign in as an active owner with the existing Pro entitlement on the company
   writer. Open Branches, Warehouses and Devices -> Online synchronization (pilot).
   Copy its binding request into a private REQUEST.txt below .buildlog.
3. Provision the isolated development company from repository root:
   python3 server/online/tool/run_local.py run bin/provision_development.dart --request ABS_REQUEST_PATH --endpoint http://127.0.0.1:45830 ABS_NEW_PRIVATE_JSON_PATH
   The command refuses an existing output and is restricted to tapbix_online_dev.
   Paste the output's activationCode into the pilot screen, review the branch and
   service address, and connect. Do not paste raw access tokens or demo identities.
4. For another enrolled branch writer, copy its binding request. On the company
   writer choose Create branch invitation and paste that request. The service
   verifies the active LAN enrollment and uses the directory's branch name. Paste
   the resulting ten-minute invitation on the matching branch writer and connect.
   Dependent warehouse/cashier devices keep their existing branch connection.
5. The screen shows last successful exchange, retry time and failures. Use Pause
   to retain pairing without automatic exchanges; resume or restart does not need
   a new code. Server-side expiry/revocation still applies to saved credentials.
This validates setup and event transport, not every accounting workflow over WAN.
The public online service release flag stays false. No paid entitlement is granted
by enabling a build flag: the server still enforces its development expiry.

Remaining S7 / S8 gates
- Authenticated company enrollment of existing branches and local identity bootstrap.
- Physical platform secure-storage validation and platform background execution.
  Pilot UI, existing permission wiring, active-app retry scheduling and independent
  transport cursors are implemented; default production builds keep them disabled.
- Apply downloaded events through existing business projectors and reconcile actual
  sale/return/transfer/report results across devices using the online transport.
- Verified commercial entitlements/webhooks, revocation/rotation and restoration.
- Full central reporting and freshness, quotas/rate limits/retention/monitoring.
- HTTPS named tunnel with access controls and public-ingress security acceptance.
- Automated backups including configuration, remote recovery exercise, load testing,
  platform builds, update paths and a limited user pilot before station 8 approval.
The API listens only on loopback. Do not expose it publicly while these gates remain.
